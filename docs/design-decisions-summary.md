# 주요 설계 결정사항 요약

## 🎯 핵심 아키텍처 결정사항

### 1. **Next.js 14 App Router 채택**

#### 결정 내용

- Next.js 14의 App Router를 사용한 파일 기반 라우팅
- Pages Router 대신 App Router 선택

#### 선택 이유

- **성능 최적화**: React Server Components 지원
- **개발자 경험**: 향상된 라우팅 시스템
- **미래 지향성**: Next.js의 권장 방향
- **SEO 최적화**: 향상된 메타데이터 관리

#### 트레이드오프

| 장점         | 단점               |
| ------------ | ------------------ |
| 더 나은 성능 | 학습 곡선 존재     |
| 향상된 DX    | 일부 기능 제한     |
| 미래 지향적  | 커뮤니티 자료 부족 |

### 2. **Valtio 상태 관리 선택**

#### 결정 내용

- Redux 대신 Valtio를 클라이언트 상태 관리로 선택
- TanStack Query와 조합하여 서버 상태 분리

#### 선택 이유

- **단순성**: 보일러플레이트 코드 최소화
- **직관성**: Proxy 기반의 자연스러운 상태 변경
- **성능**: 세밀한 리렌더링 제어
- **타입 안전성**: TypeScript와 완벽 호환

#### 비교 분석

| 상태 관리     | 복잡도 | 성능 | DX   | 학습 곡선 |
| ------------- | ------ | ---- | ---- | --------- |
| **Valtio**    | 낮음   | 높음 | 높음 | 낮음      |
| Redux Toolkit | 중간   | 중간 | 중간 | 중간      |
| Zustand       | 낮음   | 높음 | 높음 | 낮음      |
| Context API   | 낮음   | 낮음 | 낮음 | 낮음      |

### 3. **계층형 컴포넌트 아키텍처**

#### 결정 내용

- Elements → Layouts → Modules → Templates 계층 구조
- Atomic Design 패턴 적용

#### 설계 원칙

```
Templates (페이지별 특화)
    ↓
Modules (기능별 조합)
    ↓
Layouts (구조적 배치)
    ↓
Elements (기본 UI 요소)
```

#### 장점

- **재사용성**: 계층별 컴포넌트 재활용
- **유지보수성**: 명확한 책임 분리
- **확장성**: 새로운 기능 추가 용이
- **일관성**: 디자인 시스템 적용

### 4. **다국어 URL 기반 라우팅**

#### 결정 내용

- `/[lang]/page` 구조로 언어별 라우팅
- 쿠키/헤더 기반 대신 URL 기반 선택

#### 선택 이유

- **SEO 친화적**: 언어별 고유 URL
- **사용자 경험**: 명확한 언어 식별
- **캐싱 효율성**: CDN 캐싱 최적화
- **북마크 지원**: 언어별 페이지 저장 가능

#### 구현 세부사항

```typescript
// 지원 언어
const languages = ['ko', 'en', 'zh-TW']

// URL 구조
;/ko/cdoprstu /
    123 / // 한국어
    en /
    products /
    123 / // 영어
    zh -
    TW / products / 123 // 중국어(번체)
```

### 5. **도메인 기반 모듈 분리**

#### 결정 내용

- 비즈니스 도메인별 APIs, Types, Hooks 분리
- 기능 중심이 아닌 도메인 중심 구조

#### 도메인 분류

1. **사용자 관리**: Account, Auth, User
2. **학습 관리**: Course, Enrollment, Classroom
3. **상거래**: Product, Purchase, Order, Payment, Voucher
4. **콘텐츠**: Display, Banner, Search, Category

#### 이점

- **응집도 증가**: 관련 기능들의 집중
- **결합도 감소**: 도메인 간 독립성
- **팀 협업**: 도메인별 개발 가능
- **확장성**: 새 도메인 추가 용이

### 6. **Emotion CSS-in-JS + SCSS 하이브리드**

#### 결정 내용

- 컴포넌트별 스타일: Emotion CSS-in-JS
- 전역 스타일: SCSS
- 테마 시스템: 별도 파일 분리

#### 아키텍처

```
styles/
├── components/     # 컴포넌트별 SCSS
├── layout/         # 레이아웃 SCSS
├── pages/          # 페이지별 SCSS
└── utils/          # 유틸리티 SCSS

components/*/themes/ # Emotion 테마
```

#### 선택 근거

- **성능**: 런타임 스타일 최적화
- **유지보수**: 스타일과 로직 분리
- **재사용성**: 테마 기반 일관성
- **개발 효율성**: 조건부 스타일링

## 🔧 기술적 설계 결정사항

### 1. **HTTP 클라이언트 추상화**

#### 구현

```typescript
// client/http.ts - 중앙화된 HTTP 클라이언트
export const http = {
  get: (url, params, options) => fetch(...),
  post: (url, data, options) => fetch(...),
  // ... 기타 메서드
};
```

#### 이점

- **일관성**: 통일된 API 호출 방식
- **확장성**: 인터셉터, 에러 처리 중앙화
- **테스트**: 모킹 및 테스트 용이성

### 2. **타입 우선 개발**

#### 전략

- API 응답 타입 먼저 정의
- 컴포넌트 Props 타입 명시
- 유틸리티 함수 타입 안전성

#### 구조

```
types/
├── api/           # API 응답 타입
├── component/     # 컴포넌트 Props 타입
├── domain/        # 비즈니스 도메인 타입
└── utility/       # 유틸리티 타입
```

### 3. **성능 최적화 전략**

#### 코드 스플리팅

- 페이지별 자동 분할
- 컴포넌트 동적 임포트
- 라이브러리 번들 최적화

#### 캐싱 전략

- TanStack Query: 서버 상태 캐싱
- Next.js: 정적 생성 및 ISR
- 브라우저: 서비스 워커 활용

#### 이미지 최적화

```typescript
// utils/imageLoader.ts
export const imageLoader = ({ src, width, quality }) => {
    return `${CDN_URL}/${src}?w=${width}&q=${quality}`
}
```

## 📋 설계 원칙 요약
